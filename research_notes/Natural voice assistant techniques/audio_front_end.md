# Audio front-end for a macOS voice assistant: noise suppression, echo cancellation, owner isolation, VAD, far-field pickup, rejecting non-live audio

*Research notes compiled 2026-10-08 for ARES (Electron app with Swift helpers on an Apple Silicon MacBook Pro running macOS 26). What ARES does today, read from `native/AresListener.swift`: AVAudioEngine with `inputNode.setVoiceProcessingEnabled(true)`; on macOS 14+ it sets `voiceProcessingOtherAudioDuckingConfiguration` to advanced ducking OFF and level `.min`; a 1024-frame input tap feeds `SFSpeechRecognizer` (en-GB) and a rolling 16 kHz copy for voiceprint checks; Katherine's voice plays from the Electron renderer, not from this engine. The project's CLAUDE.md also notes that starting or stopping the voice-processing mic engine reconfigures the output device and makes playing audio stutter. Method: web searches until the shared search budget ran out, then direct fetches of primary pages (Apple docs, GitHub, Hugging Face, arXiv). Vendor claims are marked as such.*

## 1. Real-time noise suppression: best options, quality, latency, Apple Silicon CPU, licences, and the effect on ASR and wake words

### Takeaway
The best free, permissively licensed options that run on Apple Silicon are **DeepFilterNet3** (48 kHz; MIT/Apache-2.0; Core ML and MLX ports measured at about 0.26 ms per 10 ms hop and RTF about 0.04), **DPDFNet** (Ceva, December 2025; Apache-2.0; 8, 16 and 48 kHz models as ONNX/TFLite; supported in sherpa-onnx) and **GTCRN** (48K parameters, 33 MMAC/s; MIT; in sherpa-onnx). **RNNoise 0.2** (2024) is now the legacy baseline. On the commercial side, **Krisp** is the strongest at removing background *voices* but is priced by quote only; **Picovoice Koala** is free for personal use but checks its key online; **NVIDIA Maxine** has no macOS build. Apple's **Voice Isolation** is chosen by the user and cannot be set by an app. The most important caveat: in 2023–2026 studies, enhancement placed in front of ASR often *raises* WER even when it sounds cleaner. Judge any suppressor on WER and wake-word accuracy for the owner's own speech, not on PESQ or DNSMOS.

### Cited Findings

#### Open-source and free models
- **DeepFilterNet (Rikorose):** dual-licensed MIT / Apache-2.0. Three versions exist: DeepFilterNet (ICASSP 2022), DeepFilterNet2 (IWAENC 2022, still the default in `deep-filter` and `enhance.py`) and DeepFilterNet3 (Interspeech 2023). The project targets full-band 48 kHz audio and says it supports Linux, macOS and Windows, though training is tested only on Linux. It ships a Rust `deep-filter` binary and a LADSPA plugin for real-time mic denoising through PipeWire, and the README gives no PESQ/DNSMOS figures. Repo stats: 4.8k stars, 22 open issues, 45 PRs; maintenance status not stated — [GitHub: Rikorose/DeepFilterNet](https://github.com/Rikorose/DeepFilterNet)
- DeepFilterNet3 demo paper: real-time factor 0.19 on a single-threaded notebook CPU (Interspeech 2023 show-and-tell) — [arXiv 2305.08227](https://arxiv.org/abs/2305.08227)
- **DeepFilterNet3 Streaming Core ML** (third-party port): 48 kHz, hop of 480 samples (10 ms), fixed algorithmic latency of 1,440 samples (30 ms), 2.17M parameters. On a development Apple Silicon Mac, steady unpaced compute was **0.264 ms per hop**, and a 52.13 s clip ran in 1.494 s (34.9× real time). Swift package `DeepFilterNetCoreML` (`DeepFilterNetCoreMLStreamer.load`, `processHop`, `flush`). The Swift path's output correlated 0.999993 with the official PyTorch CLI. Licence Apache-2.0 / MIT — [Hugging Face: iky1e/DeepFilterNet3-Streaming-CoreML](https://huggingface.co/iky1e/DeepFilterNet3-Streaming-CoreML)
- **DeepFilterNet3 MLX** port, timed on an M5 Pro (network forward pass only, Python MLX): CPU-stream RTF 0.036–0.040 and GPU-stream RTF 0.027–0.029 on 5–20 s clips. 48 kHz, FFT 960 / hop 480, 2-frame (20 ms) lookahead. STFT, ERB features and deep filtering are not included in the timing — [Hugging Face: aufklarer/DeepFilterNet3-MLX](https://huggingface.co/aufklarer/DeepFilterNet3-MLX)
- A different Core ML card reports RTF 0.34 (about 3× real time) on an M2 Max. This conflicts with the iky1e figure above; the cards do not explain the gap, which is probably different compute units or measurement scopes — [Hugging Face: aufklarer/DeepFilterNet3-CoreML commit](https://huggingface.co/aufklarer/DeepFilterNet3-CoreML/commit/a9ec0b667af0653d31598b459a46fb65527ecfcf) (seen only as a search snippet)
- **GTCRN** (ICASSP 2024; Nanjing University and Horizon Robotics): 48.2K parameters and 33.0 MMAC/s (the README revised the paper's 23.7K / 39.6 MMAC/s to account for the ERB module). On VCTK-DEMAND: PESQ 2.87, SI-SNR 18.83, STOI 0.940. On the same table, DeepFilterNet (1.8M params, 0.35 GMAC/s) scores PESQ 2.81 / STOI 0.942, PercepNet (8M params) 2.73 and RNNoise (0.06M params, 0.04 GMAC/s) 2.29. On the DNS3 blind set: DNSMOS-P.808 3.44 and OVRL 2.70, against RNNoise's 3.15 and 2.53. Streaming version RTF 0.07 on an Intel i5-12400. MIT licence. Supported by sherpa-onnx since 2025-03-10. Follow-ups: UL-UNAS (2025-03), H-GTCRN (2025-05), and a community LADSPA plugin (2026-01) — [GitHub: Xiaobin-Rong/gtcrn](https://github.com/Xiaobin-Rong/gtcrn); UL-UNAS paper — [arXiv 2503.00340](https://arxiv.org/pdf/2503.00340)
- GTCRN takes 16 kHz mono input (per a third-party Rust port's model card) — [Hugging Face: vpermilp/gtcrn](https://huggingface.co/vpermilp/gtcrn)
- **DPDFNet** (Ceva, arXiv December 2025) adds dual-path RNN blocks to the DeepFilterNet2 encoder. It is causal and streaming, Apache-2.0, and ships ONNX, TFLite and PyTorch checkpoints. Variants: 16 kHz baseline 2.31M params / 0.36 GMACs; dpdfnet2 2.49M / 1.35G; dpdfnet4 2.84M / 2.36G; dpdfnet8 3.54M / 4.37G; 48 kHz "hr" models 2.58M / 2.42G and 3.63M / 7.17G; 8 kHz models too. The first output arrives after one window of about 20 ms, then one every 10 ms hop. The recommended inference path is CPU-only ONNX — [Hugging Face: Ceva-IP/DPDFNet](https://huggingface.co/Ceva-IP/DPDFNet); [arXiv 2512.16420](https://arxiv.org/abs/2512.16420). The authors say it beats other causal open models on long, low-SNR clips in 12 languages and propose a combined "PRISM" score (their own claims, not independently checked) — [PyPI: dpdfnet](https://pypi.org/project/dpdfnet/) and the search summary of the paper
- **sherpa-onnx speech enhancement** lists `gtcrn_simple` and DPDFNet (8/16/48 kHz, with an "offline attenuation limit" option). DPDFNet has both Python and **C API** pages covering offline and *online streaming* enhancement. sherpa-onnx also has Swift bindings and separate VAD and speaker-identification sections — [sherpa-onnx docs: speech enhancement](https://k2-fsa.github.io/sherpa/onnx/speech-enhancement/index.html)
- **RNNoise 0.2** (released 15 April 2024): improved training, SSE4.1/AVX2 optimisations, run-time CPU detection, and shipped weights now trained only on public datasets. No new architecture (the algorithm reference is still the 2018 paper, arXiv 1709.08243). The model file is downloaded at build time. The canonical source is gitlab.xiph.org, with GitHub as a mirror. It is used by Mumble, OBS and the PulseAudio/PipeWire noise filters — [Phoronix](https://www.phoronix.com/news/RNNoise-0.2-Released); [Xiph GitLab tags](https://gitlab.xiph.org/xiph/rnnoise/tags); [Source Mage package notes](https://src.rrz.uni-hamburg.de/files/sourcemage/codex/test/audio-libs/rnnoise/DETAILS)
- A 2025 SINERGI study of video-conference enhancement found the RNNoise variants close to real time, with DeepFilterNet3 slightly slower but still efficient (no figures in the excerpt) — [SINERGI](https://publikasi.mercubuana.ac.id/index.php/sinergi/article/view/21917)
- A September 2026 third-party test reports DeepFilterNet processing 10 minutes of audio in about 27 s on one CPU core (batch files, chip not named; low-rigour source) — [creativeainews](https://www.creativeainews.com/articles/deepfilternet-vs-rnnoise-vs-ffmpeg-noise-removal-2026/)

Processing runs locally, but the AccessKey is checked against Picovoice's servers (internet needed) and enforces account usage limits. v3.0.0 added GPU and multi-core support — [GitHub: Picovoice/koala](https://github.com/Picovoice/koala). - **Krisp SDK:** no public price. - **Krisp VIVA** ("Voice Isolation for Voice Agents"), launched July 2025, and **VIVA 2.0** (May 2026): voice isolation (v3 model), turn detection, interruption prediction (backchannel versus real barge-in) and VAD. Krisp claims under 20 ms latency, models light enough for ordinary server CPUs, and a 3.5× improvement in turn-taking accuracy (vendor claims; the Vapi listing repeats the 3.5× figure) — [Business Wire launch](https://www.businesswire.com/news/home/20250716580385/en); [Pipecat: Krisp VIVA](https://docs.pipecat.ai/pipecat/features/krisp-viva); [Speech Technology: VIVA 2.0](https://speechtechmag.com/Articles/News/Speech-Technology-News/Krisp-Launches-VIVA-2.0-an-Infrastructure-for-Voice-AI-Agents%C2%A0-174689.aspx); [Vapi partner listing](https://vapi.ai/partnerships/directory/partner/krisp-technologies-inc)

#### Apple built-in options
- Apple's voice processing (VPIO / AVAudioEngine voice processing) provides echo cancellation, noise suppression and AGC, tuned per Apple product model and audio device type. When an app uses Apple's voice processing, users get the mic modes (Standard, Voice Isolation, Wide Spectrum) for it — [WWDC23 "What's new in voice processing"](https://developer.apple.com/videos/play/wwdc2023/10235/)
- `AVCaptureDevice.preferredMicrophoneMode` is a **get-only** class property that reflects the mode the user picks in Control Center (observable with KVO), available on macOS 12+. An app cannot set Voice Isolation itself — [Apple docs: preferredMicrophoneMode](https://developer.apple.com/documentation/avfoundation/avcapturedevice/preferredmicrophonemode)
- Universal Audio warns that Mic Mode can distort or cut out audio from an interface, and that each app can have its own Mic Mode choice — [UAD help](https://help.uaudio.com/hc/en-us/articles/26704705384980)

#### Effect on ASR and wake words
- "When Audio Separation Hurts Zero-Shot ASR" (arXiv, March 2026): Meta's SAM-Audio enhancement in front of Whisper raised WER/CER in **every** model–dataset configuration tested, despite better signal-level quality. English Whisper-base WER went from 10.53% to 21.66%; Bengali large-v3 from 65.83% to 77.35% — [arXiv 2603.04710](https://arxiv.org/abs/2603.04710)
- "When De-noising Hurts" (Dec 2025 technical report): MetricGAN+ denoising made all 40 model × condition combinations worse across four ASR systems including Whisper, with semantic WER up by 1.1 to 46.6 points — [arXiv 2512.17562](https://arxiv.org/pdf/2512.17562)
- ICASSP 2023 DNS Challenge (official results, as reproduced by NPU-Elevoc): the winning personalized systems raised the subjective P.835 OVRL score (headset: noisy 1.22 → NAPSE 2.69) but **lowered word accuracy** below the unprocessed input (headset WAcc 0.843 → 0.758; the challenge baseline fell to 0.687; speakerphone 0.857 → 0.769). The challenge score = 0.5·WAcc + (OVRL−1)/8 — [ICASSP 2023 DNS Challenge paper](https://arxiv.org/pdf/2303.11510); [NPU-Elevoc system paper](https://arxiv.org/pdf/2303.06811). TEA-PSE 3.0 (Tencent) placed first in both tracks; its authors attribute the slight SIG and WAcc drops to distortion — [TEA-PSE 3.0](https://arxiv.org/pdf/2303.07704)
- VoiceFilter-Lite (Google) was trained with an *asymmetric* loss that penalises over-suppression more than under-suppression, and it adapts suppression strength to the predicted noise type, specifically so it would not hurt ASR in other conditions — [Google Research blog](https://research.google/blog/improving-on-device-speech-recognition-with-voicefilter-lite/)
- One sherpa-onnx page suggests the `dpdfnet_base` model for downstream ASR use (naming not reconciled with Ceva's "baseline") — search summary of [sherpa-onnx docs](https://k2-fsa.github.io/sherpa/onnx/speech-enhancement/index.html)

### Inferences
- For ARES, do **not** put a strong neural suppressor directly in front of `SFSpeechRecognizer` by default. The evidence (DNS-2023 WAcc drops, Whisper studies) says artifacts cost more recognition accuracy than the noise does. Better uses for a suppressor: (a) driving the VAD, barge-in and wake decisions; (b) cleaning audio before the voiceprint embedding; (c) a "wet/dry" blend (for example 70% enhanced + 30% original) or an attenuation limit (sherpa-onnx's DPDFNet exposes one), A/B-tested on the owner's own recordings for WER.
- Best free fits on Apple Silicon: DeepFilterNet3 through the Core ML streaming port (48 kHz, ~30 ms latency, ~3% of one hop's budget) if 48 kHz is kept end to end, or DPDFNet-16k / GTCRN through the sherpa-onnx C API (callable from Swift) if the pipeline is 16 kHz. All are MIT or Apache-2.0, so they suit a personal app.
- Koala's mandatory online key check and usage limits work against an always-on, offline-first assistant. Krisp BVC / VIVA is the strongest commercial option for removing *other voices* (TV, people), but it is enterprise-priced and the SDK access terms are opaque. Maxine is out (no macOS).
- Voice Isolation is free and already tuned for Mac mics, but ARES can only *detect* it and ask the user to switch it on. Because it is designed for the talker in front of the Mac, it may also suppress the owner's speech from across the room. Test before recommending it.

### Gaps
- No independent, like-for-like benchmark (same test set, same Apple Silicon machine) of DeepFilterNet3 vs DPDFNet vs GTCRN vs Koala vs Voice Isolation vs VPIO's own suppression was found. Published metrics are mostly self-reported and on different sets.
- No source quantifies how VPIO noise suppression or Voice Isolation affects `SFSpeechRecognizer` / `SpeechTranscriber` WER or wake-word false-reject rates.
- No wake-word-specific study (Porcupine, openWakeWord etc. with and without suppression) was found.
- RNNoise's licence and ARM/NEON performance were not confirmed from the pages fetched. The search budget ran out before newer 2025–2026 models (FastEnhancer, LiSenNet, ULCNet, ai-coustics SDK) and the Interspeech 2025 URGENT challenge results could be checked.
- Krisp SDK and VIVA pricing, licence terms for personal or non-commercial use, and on-device macOS availability of VIVA are not public.

## 2. Acoustic echo cancellation and barge-in on macOS: VPIO behaviour, alternatives (WebRTC AEC3, SpeexDSP), and cancelling playback that comes from another process

### Takeaway
VPIO is Apple's tuned AEC + NS + AGC. On macOS it puts **both** I/O nodes into voice processing, changes gain, ducks other apps' audio (macOS 14 added a configurable ducking level and "advanced", voice-activity-driven ducking), and has a history of low-volume, device-dependent and start-up problems. The crucial unknown for ARES is whether macOS VPIO uses audio played by *other processes* (the Electron renderer, YouTube) as its echo reference. Apple does not document this, and the evidence is mixed. The robust design gives the canceller an **explicit reference**: run **WebRTC AEC3** (BSD-3; C++ `webrtc-audio-processing` 2.x, or the pure-Rust `sonora`/`aec3` crates) and feed it either the TTS samples themselves or a **Core Audio process tap** (macOS 14.2+) of ARES's renderer or of the whole system mix. A commercial macOS SDK (RecordKit) already ships exactly this design.

### Cited Findings

#### Apple VPIO / AVAudioEngine voice processing
- Two entry points: AUVoiceIO (`kAudioUnitSubType_VoiceProcessingIO`) and AVAudioEngine's voice-processing mode, which share the same capabilities (AEC, NS, AGC, tuned per device) — [WWDC23 10235](https://developer.apple.com/videos/play/wwdc2023/10235/)
- An Apple engineer, quoting the `setVoiceProcessingEnabled(_:)` docs: voice processing needs both the input and output nodes in voice-processing mode, and enabling it on either node turns it on for the other. He adds that a slight gain change is expected when voice processing is on — [Apple Developer Forums 733733](https://developer.apple.com/forums/thread/733733); method availability macOS 10.15+ — [Apple docs: setVoiceProcessingEnabled](https://developer.apple.com/documentation/avfaudio/avaudioionode/setvoiceprocessingenabled(_:))
- **"Other audio" ducking** (macOS 14 era): any audio that is not the app's voice-chat stream counts as "other audio". VPIO mixes it with the voice audio and ducks it, by a fixed amount before this release. `AVAudioVoiceProcessingOtherAudioDuckingConfiguration` has `enableAdvancedDucking` (default off; when on, ducking follows voice activity on either side — more while someone talks, less in silence, as in FaceTime SharePlay) and `duckingLevel` (`.default` = 0, `.min` = 10, `.mid` = 20, `.max` = 30). The two settings are independent. The C equivalent is `kAUVoiceIOProperty_OtherAudioDuckingConfiguration` — [WWDC23 10235](https://developer.apple.com/videos/play/wwdc2023/10235/)
- **Muted talker detection** (new on macOS 14; first shipped on iOS 15): `inputNode.setMutedSpeechActivityEventListener` delivers `.started` / `.ended` while `isVoiceProcessingInputMuted = true`, on state changes only. AUVoiceIO equivalents: `kAUVoiceIOProperty_MutedSpeechActivityEventListener` and `kAUVoiceIOProperty_MuteOutput` — [WWDC23 10235](https://developer.apple.com/videos/play/wwdc2023/10235/)
- `isVoiceProcessingAGCEnabled`: AGC on the processed mic uplink, **on by default** (macOS 10.15+) — [Apple docs](https://developer.apple.com/documentation/avfaudio/avaudioinputnode/isvoiceprocessingagcenabled)
- Developer reports of problems (mostly older; behaviour may have changed):
  - Enabling AUVoiceProcessing lowered **both** mic and speaker gain, and turning off AGC (`kAUVoiceIOProperty_VoiceProcessingEnableAGC`) did not help. A later poster says AVAudioEngine works well on macOS 14+ with the new ducking API. Thread ran July–Dec 2023 with no accepted fix — [Forums 733733](https://developer.apple.com/forums/thread/733733)
  - VPIO output volume very low with Bluetooth output plus the built-in mic, and raising gain manually distorts — [Forums 655610](https://developer.apple.com/forums/thread/655610)
  - Playback faint even with voice processing enabled on both nodes — [Forums 742683](https://developer.apple.com/forums/thread/742683)
  - On an M1 Max MacBook Pro the first 3–6 s of each recording went missing with the flag on. VPIO is said to struggle on Spatial Audio Macs, with some Bluetooth headsets and with aggregate outputs, because its AEC needs an aggregate device and a stereo reference — [Fora Soft write-up](https://www.forasoft.com/ship-log/spatial-audio-vpio)
  - With two apps using voice processing at once (for example alongside Zoom, or Safari's Web Audio echo cancellation), one app lost its input stream (May 2024, unanswered) — [Forums 751100](https://developer.apple.com/forums/thread/751100)
  - An AEC convergence period of a few hundred ms is expected at the start of playback (Apple engineer, iOS thread) — [Forums 829784](https://developer.apple.com/forums/thread/829784)
  - Older PJSIP notes: VPIO limited to default/built-in hardware and mono only (legacy, about 10 years old) — [PJSIP ticket 1778](https://trac.pjsip.org/repos/ticket/1778)
- ARES's own observation (2026-10-06): starting or stopping the voice-processing mic engine reconfigures the output device and stutters whatever is playing — [project CLAUDE.md](file:///Users/dhruv/My%20AI/CLAUDE.md)

#### Does macOS VPIO cancel audio from other processes? (evidence is mixed)
- Apple's session says other apps' audio is mixed with the voice stream and ducked. It does not say that other audio is part of the echo reference — [WWDC23 10235](https://developer.apple.com/videos/play/wwdc2023/10235/)
- Ecamm limits its use of the built-in voice processor to setups where the Mac's built-in speakers carry the output — [Ecamm support](https://support.ecamm.com/en/articles/4001118-when-to-use-echo-cancellation)
- An iOS project found VPIO cancels echo only when it also owns the playback path, so it keeps playback in the same unit to give the AEC its reference — [voice-cat commit](https://code.iamtalon.me/Talon/voice-cat/commit/6c17881cc03ae83a0d23a543c3ff73407a7a7e79)
- Chrome's 2018 macOS-native-AEC experiment expected Apple's canceller, because of where it sits in the audio chain, to be shielded from some Chrome-side glitches. That hints it sits outside any one app (my inference, not stated) — [Chrome blog: macOS native echo cancellation](https://developer.chrome.com/blog/macos-native-echo-cancellation)
- No source was found that measures, on macOS, whether VPIO removes audio played by another process (search summary across Apple forums and vendor docs).

#### Alternatives with an explicit reference signal
- **RecordKit** (commercial macOS SDK by nonstrict) removes *system audio* from the mic in real time by capturing system audio internally as the reference. It needs macOS 14.2+ and the system-audio-recording permission (`NSAudioCaptureUsageDescription`); on macOS 26+ Screen Recording permission also grants system audio through Core Audio. Presets: Balanced (48 kHz) and Aggressive (16 kHz, stronger suppression plus a residual echo gate, recommended for speech-to-text). `AEC3Config` options: 16/32/48 kHz, balanced vs aggressive suppression, high-pass filter, residual echo gate. Output is always mono. Aggressive mode may attenuate speech and the gate can clip very quiet speech — [RecordKit echo-cancellation guide](https://nonstrict.eu/recordkit/guides/echo-cancellation.html)
- Recall.ai describes capturing system audio and feeding it to your own AEC as the reference as a common approach, and notes that results depend on the capture and sync pipeline — [Recall.ai: how to access system audio](https://www.recall.ai/blog/how-to-access-to-system-audio)
- **WebRTC audio processing:** the PulseAudio-packaged `webrtc-audio-processing` reached 2.0 on 8 Jan 2025 and 2.1 about two weeks later — [freedesktop release listing](https://distributions.freedesktop.org/software/pulseaudio/webrtc-audio-processing). The tonarino Rust wrapper (BSD-3-Clause) offers AEC, NS, AGC and VAD, plus an `experimental-aec3-config` feature that exposes EchoCanceller3 settings. Its `bundled` feature builds the C++ statically, and on macOS needs Homebrew pkg-config, meson and ninja — [GitHub: tonarino/webrtc-audio-processing](https://github.com/tonarino/webrtc-audio-processing). One downstream project hit 2.x build bugs (missing vendored submodule in the crates.io tarball for -sys 2.0.3; a meson reconfigure flag) and fell back to 0.3 (AEC2) — [wz-phone Cargo.toml / notes](https://git.manko.yoga/manawenuz/wz-phone/src/branch/feat/desktop-audio-rewrite/crates/wzp-client/Cargo.toml)
- Pure-Rust ports (pre-1.0, macOS untested): `sonora` 0.1.0 reimplements WebRTC APM (AEC3, NS, AGC2, high-pass) and has a C FFI crate — [docs.rs: sonora](https://docs.rs/crate/sonora/0.1.0); the `aec3` crate (0.1.x–0.3.0) ports AEC3 with a VoIP-style wrapper — [docs.rs: aec3](https://docs.rs/crate/aec3/0.3.0)
- One open-source project paired macOS VoiceProcessingIO with a delay-compensated NLMS stage (commit title only) — [wz-phone commit](https://git.manko.yoga/manawenuz/wz-phone/commit/d1c96cd71f4e7e5175602f85d2630f7cfa85f3fd)
- **SpeexDSP** is described only as a patent-free, open-source DSP library; development moved to gitlab.xiph.org. It is the legacy option, and its echo-canceller details were not verified here — [GitHub mirror: xiph/speexdsp](https://github.com/xiph/speexdsp)
- **Chromium/Electron:** "Chrome-wide echo cancellation" makes non-WebRTC playback (for example WebAudio/AudioContext) visible to Chrome's AEC. Zoom's SDK treats it as available from Chrome 111 on Mac, Windows and Linux (116 on ChromeOS). It is a feature-flag default rather than a guaranteed property. Zoom says browsers cannot cancel audio from *other applications* — [Zoom developer forum](https://devforum.zoom.us/t/issupportchromewideaec-sniffs-browser-name-version-breaking-echo-cancellation-on-microsoft-edge/145288); Chromium added a chrome://flags entry for it on Linux — [Chromium commit e819494](https://chromium.googlesource.com/chromium/src/+/e819494f3f791b72d6e17f722f80666159c3994b). Chromium's audio service has a loopback stream that mixes every output stream in a group into one input — [loopback_stream.h](https://chromium.googlesource.com/chromium/src.git/+/HEAD/services/audio/loopback_stream.h). An undated vendor page instead says Chromium does not echo-cancel WebAudio playback (conflicting, possibly older) — [atmoky known issues](https://docs.atmoky.com/known-issues)
- Legacy Chrome experiments: Chrome 66 let pages use Apple's macOS echo canceller (macOS 10.12+), and Chrome 68 added an experimental `echoCancellationType: browser|system` — [Chrome blog: macOS native AEC](https://developer.chrome.com/blog/macos-native-echo-cancellation); [Chrome blog: more native echo cancellation](https://developer.chrome.com/blog/more-native-echo-cancellation/)
- A June 2025 W3C TAG review (#1107) proposes letting pages choose between cancelling only remote-peer audio and cancelling *all system audio*. It has not shipped — [W3C TAG design review 1107](https://tag-github-bot.w3.org/gh/w3ctag/design-reviews/1107)
- A secondary report says Chromium's WebRTC path now includes a neural residual echo estimator that is used when a model is present. Availability is unclear — [letsdatascience report](https://letsdatascience.com/news/chrome-deploys-neural-residual-echo-estimator-3b605f3b)

#### Core Audio process taps (the reference source)
- `AudioHardwareCreateProcessTap` is available on **macOS 14.2+** — [Apple docs](https://developer.apple.com/documentation/coreaudio/audiohardwarecreateprocesstap(_:_:)). `CATapDescription` initializers cover a list of processes, a global tap that excludes listed processes (mono or stereo), and mono/stereo mixdowns of processes, optionally per device/stream. Properties include `bundleIDs`, `isExclusive`, `isMixdown`, `isMono`, `isPrivate`, `isProcessRestoreEnabled`, `muteBehavior` and `uuid` — [Apple docs: CATapDescription](https://developer.apple.com/documentation/coreaudio/catapdescription)
- Setup (AudioCap sample): translate the PID to an AudioObjectID (`kAudioHardwarePropertyTranslatePIDToProcessObject`); create the tap; create a *private* aggregate device whose `kAudioAggregateDeviceTapListKey` contains the tap UID; read `kAudioTapPropertyFormat`; run an IOProc. `NSAudioCaptureUsageDescription` must be added to Info.plist by hand. There is no public API to check or request the permission (AudioCap uses private TCC SPI). AudioCap's README says the API arrived with macOS 14.4, which conflicts with Apple's reference listing 14.2+ — [GitHub: insidegui/AudioCap](https://github.com/insidegui/AudioCap)
- A new aggregate device can take a moment to become usable, and the callback must avoid allocations, locks and logging — [DEV Community volume-mixer write-up](https://dev.to/thalesbmc/macos-still-has-no-volume-mixer-so-i-built-one-53lp)
- On macOS 26.5 beta, one developer saw taps deliver all-zero buffers for stretches of up to 16 minutes while audio was audible (unresolved) — [Forums 825780](https://developer.apple.com/forums/thread/825780)

### Inferences
- **Why ARES hears YouTube and, sometimes, Katherine:** ARES sets ducking to `.min` with advanced ducking off, so other audio plays at full level, and nothing documents that macOS VPIO uses another process's output as its echo reference. Measure it: with VPIO on, play (a) TTS from the renderer, (b) YouTube in a browser, (c) TTS through the VPIO engine's own output, and compute echo-return-loss enhancement (ERLE) on the processed mic stream for each.
- **Recommended barge-in architecture** (most robust first):
  1. **Explicit-reference AEC3 in the Swift listener.** Capture the mic *without* VPIO, run WebRTC AEC3 (BSD-3, statically linked through `webrtc-audio-processing` 2.x) at 16 or 48 kHz, and feed its far-end input from a **Core Audio process tap**. For ARES's own voice, tap the Electron renderer/ARES bundle; to also cancel YouTube or music *played on the Mac*, use one global stereo-mixdown tap. AEC3's delay estimator absorbs the tap-to-mic offset. Add the "aggressive / residual echo gate" behaviour for ASR, as RecordKit does. Costs: you lose VPIO's tuned NS/AGC and the user's Mic Mode options (replace with AGC2 and an optional neural suppressor), and you need the System Audio Recording permission.
  2. **Simpler variant:** send the exact PCM the renderer plays to the helper over IPC as the reference (no tap permission). This only cancels ARES's own voice.
  3. **Keep VPIO** but play TTS through the *same* engine (VPIO owns the reference). This is the textbook path, but it brought back the output artifacts ARES saw. Those may be linked to the reported VPIO problems on Spatial Audio Macs and with aggregate outputs, and to VPIO's mono, voice-tuned output path.
  4. Capture the mic in the renderer with `getUserMedia({echoCancellation:true})` so Chromium's AEC3 uses its own WebAudio playback as the reference (Chrome-wide AEC, Chrome 111+). This cannot cancel other apps, and it moves capture out of the Swift helper and SFSpeech.
- Whichever path is used, barge-in should be decided on the **post-AEC** signal with a VAD, a minimum speech duration (~150–300 ms) and, ideally, an owner-voice check. Softly duck the TTS on first detection and stop on confirmation (the "interrupt prediction" idea Krisp VIVA productises). Advanced ducking (`enableAdvancedDucking: true`, `.mid`) is worth an A/B test: it lowers YouTube only while someone is talking.
- The macOS-14 VPIO muted-talker listener and the HAL voice-activity property both run on echo-cancelled input. They could give ARES's standby mode a cheap "someone is talking" signal without running ASR.

### Gaps
- No primary source says whether macOS VPIO's echo reference includes other processes' output, or how large VPIO's ERLE is on MacBook Pro speakers. Needs a local measurement.
- No published ERLE / double-talk comparison of VPIO vs WebRTC AEC3 vs SpeexDSP on Apple Silicon laptops was found. The Microsoft ICASSP AEC Challenge results (2021–2023) were not reviewed (search budget exhausted).
- The root cause of the "static/pops with VPIO on the output" symptom is not documented anywhere found. Candidates: Spatial Audio speakers, aggregate-device reconfiguration, sample-rate conversion.
- Whether Electron's bundled Chromium has Chrome-wide AEC enabled by default, and whether "Enforce System Echo Cancellation"-style flags exist for macOS in current Chromium, was not verified.
- The SpeexDSP feature set and licence were not confirmed from a fetched page.

## 3. Isolating the owner's voice: personalized speech enhancement and target speaker extraction (VoiceFilter, VoiceFilter-Lite, personalized DeepFilterNet / pDNS, SpeakerBeam, newer TSE) and on-device practicality

### Takeaway
The methods are mature in research. Personalized models dominated the ICASSP 2023 DNS challenge, and there are on-device designs from Google (VoiceFilter-Lite, 2.2 MB), Amazon (Personalized PercepNet), Samsung, and 2025 edge models (TargetVoice). But **no open-source, real-time, Core ML/ONNX-packaged personalized enhancer** turned up that ARES could drop in today. The practical 2026 options are **(a)** commercial Krisp BVC / VIVA (no enrollment; not open), **(b)** gating instead of extraction (VAD segments checked against the owner's speaker embedding, i.e. a home-made "personal VAD"), or **(c)** training a personalized DeepFilterNet2-style model or using a research toolkit (WeSep) and porting it yourself.

### Cited Findings
- **VoiceFilter-Lite (Google, Interspeech 2020):** a streaming targeted-voice separation front end that works on the ASR's log-Mel filterbank features, frame by frame. Size 2.2 MB after TFLite quantization. WER improved **25.1%** on additive overlapped speech and 14.7% on reverberant overlapped speech (simulated far-field). It needs the target's d-vector enrollment and can be bypassed for non-enrolled users. Asymmetric loss against over-suppression; noise-type prediction adjusts aggressiveness — [Google Research blog](https://research.google/blog/improving-on-device-speech-recognition-with-voicefilter-lite/); [ISCA Interspeech 2020](https://www.isca-archive.org/interspeech_2020/wang20z_interspeech.html)
- **Personalized PercepNet** (AWS: Giri, Venkataramani, Valin, Isik, Krishnaswamy; Interspeech 2021) extends PercepNet to keep one target speaker in real time *without increasing complexity*. A perceptually motivated speaker embedder conditions the model, and the authors report clear gains over PercepNet on objective metrics and listening tests (no figures in the abstract) — [arXiv 2106.04129](https://arxiv.org/abs/2106.04129)
- **ICASSP 2023 DNS Challenge (DNS-5):** headset and speakerphone tracks, each allowing personalized or non-personalized entries. Most submissions were personalized. TEA-PSE 3.0 won both tracks. Interfering speakers count as errors because the reference transcript covers only the primary speaker — [ICASSP 2023 DNS Challenge](https://arxiv.org/pdf/2303.11510); [Microsoft challenge page](https://www.microsoft.com/en-us/research/academic-program/deep-noise-suppression-challenge-icassp-2023); [TEA-PSE 3.0](https://arxiv.org/pdf/2303.07704)
- **Personalized DeepFilterNet2** (HSCMA 2024, an ICASSP 2024 satellite): speaker embeddings injected into DeepFilterNet2's dual-stage design. The authors test where to inject them and report much better quality with minimal extra compute (no numbers in the abstract) — [arXiv 2404.08022](https://arxiv.org/abs/2404.08022)
- Samsung (Interspeech 2023): cross-attention over the full enrollment recording instead of one static speaker vector; better than leading systems at half the model size and with lower latency, on an on-device-like dataset — [ISCA Interspeech 2023](https://www.isca-archive.org/interspeech_2023/zhang23r_interspeech.html)
- **TargetVoice (Interspeech 2025):** small-footprint TSE for edge devices. Speaker encoder about 10 MB using a single 3 s enrollment; extractor about 12 MB at about 6 GMACs. The authors say streaming only the enrolled voice improves ASR in real-world noise. Latency and SI-SDR/WER numbers are not in the abstract — [ISCA Interspeech 2025](https://www.isca-archive.org/interspeech_2025/pallala25_interspeech.html)
- Other 2024–2025 real-time TSE work: Fraunhofer IDMT (EUSIPCO 2025), whose linear self-attention separator beat standard attention with a lower RTF — [Fraunhofer publica](https://publica.fraunhofer.de/handle/publica/508056); DSINet (ICASSP 2025; metadata only) — [DOI](https://doi.org/10.1109/icassp49660.2025.10887817); SpeakerBeam-SS (2024), whose state-space model cut RTF by 78% versus a causal Conv-TasNet baseline — [summary](https://awesomepapers.io/speech-audio/papers/sato2024speakerbeam); autoregressive embeddings from already-extracted speech for frame-by-frame TSE (ICASSP 2025 submission) — [arXiv 2409.06136](https://arxiv.org/abs/2409.06136)
- **WeSep** (WeNet team, Interspeech 2024): open TSE toolkit with flexible speaker modelling, on-the-fly simulation, recipes and some deployment support (ONNX not confirmed) — [arXiv 2409.15799](https://arxiv.org/abs/2409.15799); code at github.com/wenet-e2e/WeSep
- The **SLT 2026 REAL-TSE Challenge** (real conversational recordings) caps the online track's algorithmic latency at 100 ms — [arXiv 2607.15198](https://arxiv.org/pdf/2607.15198)
- Self-supervised personalization with little clean target speech and fewer parameters (zero/few-shot) — [Sivaraman & Kim, IEEE JSTSP 2022](https://par.nsf.gov/servlets/purl/10400775)
- Product patents describe falling back to non-personalized enhancement when no embedding exists — [USPTO 12518764](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12518764) — and per-participant personalized models with about 45 dB suppression of other sounds — [USPTO 12387738](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12387738)
- **Krisp BVC** removes nearby voices with no enrollment (a model that isolates a headset wearer) — [Vapi partner listing](https://vapi.ai/partnerships/directory/partner/krisp-technologies-inc); VIVA voice isolation sits in front of VAD and keeps only the main talker — [Pipecat: Krisp VIVA](https://docs.pipecat.ai/pipecat/features/krisp-viva)
- sherpa-onnx offers GTCRN/DPDFNet enhancement and a separate speaker-identification section (speaker embeddings) but no TSE model on its enhancement page — [sherpa-onnx speech enhancement](https://k2-fsa.github.io/sherpa/onnx/speech-enhancement/index.html)

### Inferences
- VoiceFilter-Lite's design (it works on ASR features inside Google's recognizer) cannot be reproduced with Apple's `SFSpeechRecognizer`, which only takes audio buffers. ARES would need a *waveform* personalized enhancer (pDFN2 / Personalized PercepNet / TargetVoice style) or a gating approach.
- Practical now: **owner-gating**. VAD segments → speaker embedding (ARES already has a voiceprint; sherpa-onnx's speaker-ID models are an on-device ONNX option) → accept only when the similarity passes a threshold, re-checked over a sliding window during long utterances. That handles "TV or other people talking", but not "owner talking *over* the TV" (overlap), where only TSE or BVC helps.
- If ARES invests in TSE later: a pDFN2-style model is the most natural fit (same family as DeepFilterNet, permissive licence, low overhead). Use asymmetric over-suppression penalties like VoiceFilter-Lite's, and keep a bypass when confidence is low, given the DNS-2023 WAcc losses.

### Gaps
- No open, pretrained, real-time personalized enhancement / TSE checkpoint with Core ML or ONNX streaming export was found (pDFN2, Personalized PercepNet and TargetVoice weights appear unpublished; WeSep's export path is unconfirmed).
- No Apple Silicon latency or CPU measurements for any TSE model were found.
- No quantitative numbers for pDFN2, Personalized PercepNet or TargetVoice beyond the abstracts were retrieved.

## 4. Voice activity detection: Silero (latest), WebRTC VAD, TEN VAD, Apple's built-in options, personal VAD, and the effect on end-of-speech detection

### Takeaway
**Silero VAD v6.x** (v6.0 Aug 2025 → v6.2.3 Sep 2026, years inferred; MIT; 32 ms chunks; under 1 ms per chunk on one CPU thread; a Core ML port exists) has the best published accuracy and by far the best *noise rejection* (ESC-50 noise accuracy 0.87 vs 0.42 for TEN and 0.00 for WebRTC, on Silero's own wiki). **TEN VAD** (Agora; Apache-2.0 *with additional conditions*; 10/16 ms hops; RTF 0.016 on M1; macOS framework) claims faster speech-to-silence transitions, which matter for end-of-turn latency. Each project's own benchmark favours itself. **WebRTC VAD** is legacy. Apple offers a HAL voice-activity property on echo-cancelled input (macOS 14) and `SpeechDetector` (macOS 26), but the latter only gates `SpeechTranscriber` and emits no speech events. A true **personal VAD** exists only in Google papers, with no open model.

### Cited Findings
- **Silero VAD:** MIT per the repo sidebar (the badge alt text says CC BY-NC 4.0, an inconsistency on the page); 8 and 16 kHz; a chunk of 30+ ms takes under 1 ms on a single CPU thread; JIT model about 2 MB; ONNX via `silero-vad[onnx-cpu]`, which can be 4–5× faster in some conditions — [GitHub: snakers4/silero-vad](https://github.com/snakers4/silero-vad)
- Silero releases (the page shows no years; years below are inferred from ordering and other sources): **v6.0 (26 Aug [2025])**, 16% fewer errors on noisy real-life data and 11% fewer on multi-domain validation, a new training algorithm, known problems with voice-like instruments and very high-pitched voices; **v6.2 (06 Nov [2025])**, reworked training and better robustness on out-of-distribution input, child/cartoon voices, muted speech and low-quality phone calls; v6.2.1 (24 Feb [2026]), onnxruntime made optional; v6.2.2 (17 Sep [2026]), an offline ONNX sequence model that releases the GIL; v6.2.3 (23 Sep [2026]), torchaudio optional. v5.1 (09 Jul) and v5.1.1/5.1.2 (09 Oct) were the 2024 line — [GitHub releases](https://github.com/snakers4/silero-vad/releases); v6.2 announcement (Silero team, Habr) — [Habr](https://habr.com/en/users/snakers4/posts); whisper.cpp moved its VAD examples from v5.1.2 to v6.2.0 — [whisper.cpp PR 3524](https://github.com/ggml-org/whisper.cpp/pull/3524/files)
- **Silero's quality wiki** (Silero's own benchmark; 31.25 ms segments). ROC-AUC on the 17 h multi-domain set: WebRTC 0.73, Silero v5 0.96, **v6 0.97**, TEN VAD 0.93, FireRed VAD 0.94, an unnamed commercial VAD 0.93. Speech accuracy (threshold tuned on multi-domain): WebRTC 0.74, v5 0.91, v6 0.92, TEN 0.87. **Noise-only accuracy** on ESC-50 / private noise: WebRTC 0.00 / 0.15, v5 0.61 / 0.44, **v6 0.87 / 0.71**, TEN 0.42 / 0.47 — [Silero wiki: Quality Metrics](https://github.com/snakers4/silero-vad/wiki/Quality-Metrics)
- Silero v6.2.1 Core ML port: a 32 ms streaming model (512 new samples per call at 16 kHz) and a 256 ms model (4096 samples) — [Hugging Face: aufklarer/Silero-VAD-v6.2.1-CoreML](https://huggingface.co/aufklarer/Silero-VAD-v6.2.1-CoreML)
- **TEN VAD** (TEN framework / Agora): Apache 2.0 plus additional conditions in its LICENSE file (pitch-estimation code derived from LPCNet under BSD). Platforms include macOS arm64 and x86_64 (C, Java, Go), iOS, Android, Linux, Windows and WASM. 16 kHz input with hops of 160 or 256 samples (10/16 ms); default threshold 0.5, to be tuned per domain. RTF 0.0160 on an M1 Mac, macOS library 731 KB; RTF 0.0086 vs Silero's 0.0127 on a Xeon Gold 6348. It claims the best precision-recall on its own annotated test set (LibriSpeech, GigaSpeech and DNS clips, test set included in the repo) and says Silero lags by several hundred ms at speech-to-silence transitions and misses short pauses. ONNX model released June 2025 (ORT ≥ 1.17.1); WASM build Nov 2025 — [GitHub: TEN-framework/ten-vad](https://github.com/TEN-framework/ten-vad)
- Agora says switching its LiveCap product from Silero to TEN cut false detections from 67% to under 5% (vendor case; counting method not given) — [Agora blog](https://www.agora.io/es/blog/the-open-source-vad-upgrade-that-benefits-billions-of-live-stream-viewers)
- **Apple HAL VAD (macOS only, introduced in the WWDC23 / macOS 14 session):** set `kAudioDevicePropertyVoiceActivityDetectionEnable` on the input device and listen to `kAudioDevicePropertyVoiceActivityDetectionState`. Detection runs on **echo-cancelled** mic input and works regardless of process mute — [WWDC23 10235](https://developer.apple.com/videos/play/wwdc2023/10235/); [Apple docs: kAudioDevicePropertyVoiceActivityDetectionEnable](https://developer.apple.com/documentation/coreaudio/kaudiodevicepropertyvoiceactivitydetectionenable)
- **Apple `SpeechDetector` (macOS 26+):** a VAD module for `SpeechAnalyzer` that gates transcription to save power. It works *only* together with `SpeechTranscriber` or `DictationTranscriber`. Its `results` currently support only VAD error handling, and `SensitivityLevel` (medium recommended) sets how aggressive it is. Apple warns that always-on VAD can drop real speech and lower accuracy — [Apple docs: SpeechDetector](https://developer.apple.com/documentation/speech/speechdetector)
- **Personal VAD (Google):** a frame-level VAD conditioned on the target speaker's embedding or speaker-verification score, which gates a streaming on-device ASR. 130K parameters (Google's page says 130 KB, a unit conflict) — [arXiv 1908.04284](https://arxiv.org/pdf/1908.04284); [Google Research](https://research.google/pubs/personal-vad-speaker-conditioned-voice-activity-detection/). **Personal VAD 2.0** (Interspeech 2022) adds enrollment-less training, streaming and a smaller runtime footprint — [arXiv 2204.03793](https://arxiv.org/abs/2204.03793)
- Krisp VIVA bundles a VAD, a streaming end-of-turn model (multilingual, audio-only, waits out mid-sentence pauses) and interruption prediction (backchannel vs barge-in), usable in Pipecat as an alternative to Smart Turn — [Pipecat: Krisp VIVA](https://docs.pipecat.ai/pipecat/features/krisp-viva); [Speech Technology](https://speechtechmag.com/Articles/News/Speech-Technology-News/Krisp-Launches-VIVA-2.0-an-Infrastructure-for-Voice-AI-Agents%C2%A0-174689.aspx)

### Inferences
- Default choice: **Silero v6.2** (MIT, strongest noise rejection, so fewer TV, keyboard and YouTube false starts) at 16 kHz on the post-AEC stream. Run **TEN VAD** alongside it, or use it only for *end-of-speech* timing if measurements on ARES audio confirm TEN's faster speech-to-silence transition. Both are cheap: TEN is about 1.6% of real time on an M1 (RTF 0.016), and Silero stays under about 3% (under 1 ms per 32 ms chunk on one CPU thread; no Apple Silicon figure published).
- End-of-speech latency comes mostly from hangover settings (minimum silence before "done"), not from the model. Tune the silence threshold per mode (wake-word command vs conversation) and pair the VAD with a semantic or turn-taking model (covered elsewhere).
- Apple's HAL VAD is a free, echo-cancelled "someone is speaking" flag for standby or wake gating. `SpeechDetector` is useful only if ARES moves to `SpeechAnalyzer`, and even then it gives no speech start/end events.
- "Personal VAD" for ARES = VAD + streaming owner verification on each segment (see section 3). There is no ready-made model, but the pieces are available on-device.

### Gaps
- No *independent* VAD benchmark comparing Silero v6.x and TEN VAD on far-field, TV-noise, Mac-speaker echo conditions was found; both published comparisons are by interested parties and disagree.
- No measured speech-end latency numbers (in ms) for Silero v6 vs TEN were found; TEN's "several hundred ms" claim about Silero is qualitative.
- The exact precision and recall of Apple's HAL VAD and `SpeechDetector` are undocumented.
- The additional conditions in TEN VAD's licence were not read; check them before shipping.
- Picovoice Cobra (commercial VAD) was not researched.

## 5. Far-field pickup and gain: MacBook mic array, beamforming, AGC and gain staging, dereverberation (WPE), and macOS Mic Modes (selection, detection, interaction with VPIO)

### Takeaway
The MacBook Pro's three-mic array (high SNR, directional beamforming) is beamformed in Apple's software for a talker **in front of the keyboard**. Apps get one processed input stream, not the raw mics. Across-the-room speech therefore arrives quieter, more reverberant and possibly attenuated by the beam (and by Voice Isolation if it is on). Apps **cannot set** the mic mode (`preferredMicrophoneMode` is get-only). They can observe it and show the system picker, and mic modes apply when the app uses Apple's voice processing. The real fixes for distance are gain staging (VPIO AGC is on by default; add a software AGC before ASR), possibly an external far-field array with hardware AEC and beamforming (XMOS XVF3800 class), and treating WPE-style dereverberation as optional and multichannel-oriented.

### Cited Findings
- Current MacBook Pro (M5 / M5 Pro / M5 Max) spec: "Studio-quality three-mic array with high signal-to-noise ratio and directional beamforming". It also lists Voice Isolation and Wide Spectrum mic modes and a six-speaker system with force-cancelling woofers and Spatial Audio — [Apple MacBook Pro tech specs](https://www.apple.com/macbook-pro/specs/)
- Asahi Linux: the raw MacBook mics are PDM mics routed through the always-on processor (AOP). They are highly omnidirectional and very sensitive; Apple's beamforming narrows pickup, so the result depends on hardware and software together. The open-source "Triforce" beamformer probably falls short of macOS quality — [Asahi Linux audio docs](https://asahilinux.org/docs/sw/audio-userspace/); [Liliputing](https://liliputing.com/asahi-linux-adds-microphone-support-for-macbooks-with-apple-silicon/). MacGeneration: the processing combines the directional signals assuming the user sits in front of the keyboard — [MacGeneration](https://www.macg.co/logiciels/2025/03/asahi-linux-prend-en-charge-le-microphone-des-mac-portable-et-ca-ete-complique-300545)
- **Mic modes API:** `AVCaptureDevice.MicrophoneMode` (standard, wideSpectrum, voiceIsolation), macOS 12+ — [Apple docs: MicrophoneMode](https://developer.apple.com/documentation/avfoundation/avcapturedevice/microphonemode); `preferredMicrophoneMode` is get-only and reflects the user's Control Center choice (observable with KVO) — [Apple docs](https://developer.apple.com/documentation/avfoundation/avcapturedevice/preferredmicrophonemode); `SystemUserInterface.microphoneModes` presents the system mode picker (macOS 12+) — [Apple docs: microphoneModes](https://developer.apple.com/documentation/avfoundation/avcapturedevice/systemuserinterface/microphonemodes); `activeMicrophoneMode` reports the current mode — [Forums 757948](https://developer.apple.com/forums/thread/757948)
- Mic Mode needs a 2018-or-newer Mac (forum reply quoting WWDC21) — [Forums 740917](https://developer.apple.com/forums/thread/740917). An App Store build on Intel Macs always reported Standard, while M1/M2 Macs and non-App-Store builds reported correctly — [Forums 741658](https://developer.apple.com/forums/thread/741658). An iOS developer could not find a public way to *select* Voice Isolation — [Forums 844448](https://developer.apple.com/forums/thread/844448)
- Mic modes are offered to the user when apps use Apple's voice processing — [WWDC23 10235](https://developer.apple.com/videos/play/wwdc2023/10235/). On iOS, Voice Isolation is unavailable when echo cancellation is off (iOS-specific vendor note) — [Phenix docs](https://phenixrts.com/docs/knowledge-base/how-to/ios-audio-pipelines/)
- WWDC25 "Enhance your app's audio recording capabilities" added an input picker with mic-mode selection (`AVInputPickerInteraction`, iOS context), AirPods high-quality recording, FOA spatial capture and **Audio Mix** (speech vs ambience separation through `CNAssetSpatialAudioInfo` / `AUAudioMix`). Audio Mix works on *recorded* spatial audio (iOS and macOS 26), not on live Mac mic input — [WWDC25 session 251](https://developer.apple.com/videos/play/wwdc2025/251/)
- **AGC:** VPIO uplink AGC (`isVoiceProcessingAGCEnabled`) is on by default — [Apple docs](https://developer.apple.com/documentation/avfaudio/avaudioinputnode/isvoiceprocessingagcenabled). Developers report VPIO lowering mic gain and AGC-off not restoring it — [Forums 733733](https://developer.apple.com/forums/thread/733733). WebRTC APM includes AGC (and AGC2 in the `sonora` port) — [tonarino crate](https://github.com/tonarino/webrtc-audio-processing); [sonora](https://docs.rs/crate/sonora/0.1.0)
- **External far-field hardware:** the XMOS XVF3800 does AEC (claimed to work even at high speaker volume), stationary and non-stationary noise suppression, adaptive free-running and focused beamformers with direction-of-arrival estimation (said to improve double-talk and dereverberation), and configurable AGC. Its 4-mic dev kit (XK-VOICE-SQ66) offers 100 mm linear or 66 mm square layouts, USB 2.0 audio and I2S. Firmware v3.2.1 (2024-10-30); datasheet 2026-03-17; no price on the page — [XMOS XVF3800](https://www.xmos.com/xvf3800/)
- **Dereverberation:** NARA-WPE (MIT) implements offline iterative, block-online and recursive frame-online WPE in NumPy and TensorFlow, based on multichannel linear prediction (Yoshioka & Nakatani 2012). Latency and cost are not discussed — [GitHub: fgnt/nara_wpe](https://github.com/fgnt/nara_wpe). NVIDIA Maxine offers a dereverb plus denoise effect, but not on macOS — [NVIDIA Audio Effects SDK](https://developer.nvidia.com/audio-effects-sdk)
- VoiceFilter-Lite's gains were smaller on *reverberant* (far-field-like) overlapped speech (14.7%) than on additive overlap (25.1%) — [Google Research blog](https://research.google/blog/improving-on-device-speech-recognition-with-voicefilter-lite/)

### Inferences
- **Low input gain (missed speech):** measure the level *after* VPIO (AGC on by default) at desk and across-room distances. Check the macOS input volume for the built-in mic. Then add a software AGC (WebRTC AGC2 through `webrtc-audio-processing` / `sonora`) after AEC and NS but **before** VAD and ASR, targeting roughly −26 to −20 dBFS speech with a limiter, so distant speech reaches the recognizer at a consistent level. ARES's fixed RMS threshold (0.015) and start-up "noise floor" learning should be revisited once AGC is in place, because a fixed threshold misses quiet distant speech.
- **Mic Mode:** KVO-observe `AVCaptureDevice.preferredMicrophoneMode` / `activeMicrophoneMode` and surface the state in ARES's menu. Offer `showSystemUserInterface(.microphoneModes)` as a one-click "turn on Voice Isolation", but only after A/B-testing it on across-room owner speech and on WER. If ARES drops VPIO for its own AEC3 pipeline, assume the Mic Mode options disappear for the listener (per WWDC23 they are tied to voice processing).
- **Across the room:** the built-in array's front-facing beam plus reverberation is a hard limit. The highest-value upgrade is an external far-field array with on-board AEC and beamforming (XVF3800 class, or a conference speakerphone). Its AEC only works if ARES's TTS **plays through that device** (USB output) or the board gets the reference over I2S.
- WPE is mainly a multichannel tool. On the single beamformed stream macOS exposes, expect limited gains. Neural suppressors (DFN3/DPDFNet) partly reduce late reverb, but their ASR side effects (section 1) apply here too.

### Gaps
- No measured specs (SNR, polar pattern, beam width, sample rate) for the MacBook Pro array, and no documentation of how Apple's beamforming treats off-axis or across-room talkers.
- Whether an app can open the raw multi-mic channels on Apple Silicon Macs (for its own beamforming or WPE) was not established.
- Whether Mic Mode (Voice Isolation) applies to a helper process that uses AVAudioEngine voice processing, and how Voice Isolation interacts with VPIO's own NS/AGC, is undocumented.
- No price or availability was found for XVF3800-based USB arrays (for example Seeed ReSpeaker variants); the search budget ran out.
- No real-time single-channel neural dereverberation model with Apple Silicon numbers was found.

## 6. Rejecting audio that isn't a live person in the room: detecting sound the Mac itself is playing (AEC reference, Core Audio process taps) and telling near-field speech from a TV across the room

### Takeaway
For sound **the Mac itself plays** (Katherine, YouTube, music), the reliable tool is a **Core Audio process tap** (macOS 14.2+). It gives an exact copy of the Mac's output, to use as (1) the AEC reference, (2) a "the Mac is playing speech right now" detector, and (3) a transcript or wake-word cross-check, in the spirit of Amazon's self-wake suppression patent. For a **TV or people in the room**, signal processing alone is weak (single-channel distance estimation is research-grade, errors around 0.5 m on real recordings). The strongest practical signal is **owner verification** (voiceprint and personal-VAD style gating), helped by loudness and distance cues and, with a mic array, direction-of-arrival "stationary source" heuristics like the Echo's.

### Cited Findings
- **Process taps:** `AudioHardwareCreateProcessTap` (macOS 14.2+) and `CATapDescription` can tap specific processes or `bundleIDs`, or a global mono/stereo mix *excluding* listed processes; `muteBehavior` controls whether the tapped audio still reaches the speakers — [Apple docs: AudioHardwareCreateProcessTap](https://developer.apple.com/documentation/coreaudio/audiohardwarecreateprocesstap(_:_:)); [Apple docs: CATapDescription](https://developer.apple.com/documentation/coreaudio/catapdescription). The tap input stream is a mix of all the specified processes' output — [Apple docs: CATapDescription](https://developer.apple.com/documentation/coreaudio/catapdescription)
- Commercial precedent for system-audio-referenced AEC on macOS 14.2+ (RecordKit; aggressive 16 kHz preset with a residual echo gate for speech-to-text) — [RecordKit guide](https://nonstrict.eu/recordkit/guides/echo-cancellation.html)
- **Self-wake suppression (Amazon patent):** run a wake-word recognizer on the audio the device is *about to play*; if the wake word appears there, a mic-side detection at about the same moment is discarded — [USPTO 11004453 "Avoiding wake word self-triggering"](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/11004453)
- **Broadcast/ad rejection (Amazon):** acoustic fingerprints (overlapping windows starting about every 10 ms) of clips arriving from many devices are matched in the cloud, which blocks other units from acting on the same clip. Amazon estimates 80–90% of units stay quiet during broadcast events. Planned ads are easy; unplanned TV dialogue is harder. **Live talker vs TV:** recorded sources tend to stay in one place while people move. The Echo's 7-mic ring uses about 200 µs timing differences to estimate direction, so a trigger from a fixed, constantly noisy spot points to a TV or radio — not foolproof — [EE Journal: Teaching Alexa to ignore your TV](https://www.eejournal.com/article/teaching-alexa-to-ignore-your-tv-2/); [Popular Science](https://www.popsci.com/?p=31648); [SlashGear](https://www.slashgear.com/alexa-wont-be-paying-attention-to-amazons-super-bowl-ad-02517898/)
- An accidental-trigger study of smart speakers stresses that TV audio makes false accepts and false rejects both costly — [arXiv 2008.00508](https://arxiv.org/pdf/2008.00508)
- **Single-channel speaker distance estimation:** Neri et al. (IEEE/ACM TASLP 2024) regress continuous distance with an attention CRNN on STFT magnitude plus phase sin/cos. Error is about 11 cm in noise-free synthetic rooms, about 1.3 m in a hybrid setting and about 0.5 m on real recordings; code and models are public — [arXiv 2403.17514](https://arxiv.org/html/2403.17514v1). Earlier single-mic work (WASPAA 2023) reached centimetre-level errors on clean audio but degraded sharply with WHAM! noise — [Tampere University research portal](https://researchportal.tuni.fi/en/publications/single-channel-speaker-distance-estimation-in-reverberant-environ/) (seen only as a search summary). A 2026 preprint studies how early and late reverberation affect it — [arXiv 2605.07694](https://arxiv.org/pdf/2605.07694)
- **Near/far separation with one mic:** a 1.5 m cutoff with one near talker and up to four far talkers gave up to 4.4 dB SI-SNR improvement (Interspeech 2022) — [Patterson et al., Interspeech 2022](https://www.isca-archive.org/interspeech_2022/patterson22_interspeech.pdf)
- Owner-conditioned gating (Personal VAD / VoiceFilter-Lite) is the published on-device approach to ignoring non-target speakers — [Personal VAD](https://arxiv.org/pdf/1908.04284); [VoiceFilter-Lite blog](https://research.google/blog/improving-on-device-speech-recognition-with-voicefilter-lite/)
- ARES already checks a voiceprint without the wake word in desk mode, and overheard speech is never logged, sent to the brain or subtitled — [project CLAUDE.md](file:///Users/dhruv/My%20AI/CLAUDE.md)

### Inferences
- **Mac-originated audio, three layers, all fed by one global stereo-mixdown tap.** (1) Tap → AEC3 far-end reference (removes most of it acoustically). (2) Tap → the same VAD → "Mac is speaking" flag. When mic speech coincides with tap speech and the post-AEC residual correlates with the tap, discount it. (3) Tap → cheap ASR or wake-word pass. Drop mic transcripts or wakes that match what the Mac just played within about 1–2 s (the Amazon patent's idea, extended to whole transcripts). Also discard any mic transcript that matches ARES's own current TTS text, which needs no tap at all.
- **TV or people in the room:** rely on owner verification first (accept commands only when the voiceprint matches, re-checked as the utterance grows). Add a "near-field score" from cheap features (level after AGC, a direct-to-reverberant proxy, spectral tilt). Treat Neri-style distance models as an experiment, not a gate. With an external array (XVF3800 has DoA), add the Echo-style stationary-direction prior for the TV's location.
- Since **ARES also keeps overheard speech private**, owner gating should happen *before* any text leaves the listener, which matches ARES's existing desk-mode rule.

#### Suggested ARES front-end (synthesis across sections)
1. Capture: built-in mic at 48 kHz. Either (A) keep VPIO with ducking A/B-tested (`.min` vs advanced `.mid`) **and** measure whether it cancels renderer and YouTube playback, or (B, preferred if A fails the measurement) raw capture + **WebRTC AEC3** with a **global Core Audio tap** as the reference (macOS 14.2+, System Audio Recording permission).
2. Optional light neural NS (DeepFilterNet3 Core ML at 48 kHz, or DPDFNet/GTCRN at 16 kHz through sherpa-onnx), used mainly for detection paths, with an attenuation limit or dry/wet blend for the ASR path. Accept it only if the owner's WER does not get worse.
3. Software AGC (AGC2) → resample to 16 kHz → **Silero v6.2** VAD (with TEN VAD for endpoint timing if it proves faster on ARES audio) → owner verification on segments → ASR (`SFSpeechRecognizer` / `SpeechTranscriber`).
4. Barge-in decided on the post-AEC signal: VAD plus minimum duration plus owner match; duck the TTS, then stop it.
5. Tap-based self-echo and "Mac is playing" suppression plus TTS-text matching. Mic Mode surfaced to the user, not forced.
6. Hardware path for true across-the-room use: an XVF3800-class USB array with TTS played through it.

### Gaps
- No primary source quantifies how well process-tap-referenced AEC3 cancels laptop-speaker echo on a MacBook Pro (ERLE, double-talk), or the tap's added latency and jitter. RecordKit gives presets but no numbers.
- The macOS 26.5-beta "all-zero tap buffers" bug is unresolved; its status in the shipping macOS 26.x was not established.
- No published, deployable method for telling a *TV across the room* from a near-field live talker on a single beamformed laptop stream was found. Loudspeaker-vs-live "liveness" detection (replay/voice anti-spoofing literature) was not reviewed (search budget exhausted).
- No Apple or Google documentation describing their current TV-rejection methods was found. The Amazon material dates from about 2017–2018.
